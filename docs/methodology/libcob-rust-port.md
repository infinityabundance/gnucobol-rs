# How the libcob runtime was ported to Rust (methodology)

This is the authoritative account of how the `gnucobol-rs` runtime was produced from the admitted
GnuCOBOL 3.2 `libcob` sources. It exists because the derivation model of the runtime and the
derivation model of the parser/front-end are DIFFERENT, and conflating them is how "clean-room"
claims go wrong. The short version: the runtime is a **faithful copyleft derivative port**
(LGPL-3.0-or-later), NOT a clean-room reimplementation; the parser/front-end is documented
separately in [`parser-front-end-provenance.md`](parser-front-end-provenance.md).

## 0. The one-line position

- The runtime crate (`crates/gnucobol-rs`) is a **statement-by-statement Rust port of the admitted
  GnuCOBOL 3.2 `libcob` runtime** — a derivative work under copyright, inheriting
  **LGPL-3.0-or-later**. It is **not** clean-room: the upstream `.c` files were read directly and
  mirrored function-for-function, with upstream line citations in the Rust comments
  (e.g. `// move.c:477` for `cob_move_display_to_packed`).
- "Clean-room" in this project refers ONLY to the separately written parser/front-end, and even
  there only as the author's committed claim — see the parser provenance document for the
  verification limits.

## 3. Translation method

Per [`docs/porting-method.md`](../porting-method.md), the port follows a fixed, oracle-first order:

1. **Admit.** Pin the upstream release by sha256; never vendor it into the published crate.
2. **Read.** Read the upstream source completely before writing Rust — entry points, dispatch,
   helper macros, byte/return semantics (e.g. for the decimal slice: `libcob/move.c`,
   `libcob/numeric.c`, `libcob/common.c`, `libcob/coblocal.h`, `libcob/common.h`).
3. **Build the oracle.** Compile the real upstream into `lab/oracle/prefix`; that binary — not the
   reading — is the source of truth.
4. **Port faithfully, with citations.** Mirror upstream control flow, not just outputs; cite the
   upstream line for each ported block (`// move.c:477`). Reproduce quirks, padding, and
   undefined-but-observed choices exactly.
5. **Prove parity.** Feed identical input rows to the C oracle and the Rust mirror; compare full
   byte streams.
6. **Fixtures / sweep / kani / fuzz / gate.** Committed `(input, expected)` fixtures, differential
   sweeps, one reduced kani invariant, a detached fuzz crate, and the release gates.

So this is a **source translation with behavioral verification against the built oracle** — not a
semantic reimplementation from the COBOL spec, and not a mechanical line-for-line converter. The
function names and control-flow structure are retained (that is what makes it a derivative), the
comments carry the upstream line references, and the LICENSE is inherited (LGPL-3.0-or-later).

## 5. How C runtime semantics were mapped to safe Rust

| C construct | Rust mapping (as implemented) |
|---|---|
| global mutable runtime state | module-scoped thread-locals (`thread_local!` + `Cell`/`RefCell`), reset per run-unit |
| pointers / aliasing / unions | typed `Field`/`FieldAttr` models; byte buffers (`Vec<u8>`) for storage; no raw pointers (`#![forbid(unsafe_code)]`) |
| allocation / lifetime | owned buffers; explicit byte-vector storage instead of `malloc`/`free` |
| `setjmp`/`longjmp` (STOP RUN, exceptions) | explicit control-flow signals (stop/exit flags + `Result`-based unwinding) at the interpreter boundary; runtime primitives return errors |
| `errno`-style file/IO state | typed `RunError` / file-status codes |
| undefined-but-observed behavior | reproduced exactly where the oracle observes it; otherwise fails closed |

The detailed mapping for each function is in the source comments and the parity reports; this
table is the general pattern, not a per-function promise.

## 6. What "1:1" means here — and does not mean

- **Symbol inventory:** 100% of compiled `libcob` functions have a real Rust `fn` (LIBCOB-PARITY.md).
- **Behavior:** byte-identical where a sealed court proves it — the per-court oracle sweeps
  (`lab/verify-sealed-courts.sh`, 109 sweep scripts) compare full byte streams against
  the admitted oracle. The whole-tree census shows 88 of 329 libcob functions
  with a direct Rust counterpart.
- **NOT claimed:** "1:1" does NOT mean every byte of every function is proven equal; it means the
  symbol inventory is complete and the sealed corpus is byte-equal. Untested paths are non-claims.

## 8. Explicit non-claims

- The runtime is NOT clean-room, NOT permissively licensed by choice, and NOT "written from the
  spec": it is a faithful derivative of `libcob`.
- Not every `libcob` function is behaviorally proven byte-equal; only the sealed corpus is.
- The parser/front-end provenance is a SEPARATE question (next document).
- A Rust port is not "the same binary": build environment, toolchain and libc identities are
  recorded per court, and behavior is proven per court, not assumed.
